# 文章生成分镜

这份文档规定**怎么从一篇文章产出一份能直接渲染的分镜脚本**。它是「文章 → 分镜」这一步的权威来源：
步骤、判断顺序、约束与交付条件都写在这里，其他文档只链接、不复述。

生成动作由 AI 工具按本文档执行；**项目不含生成器程序**，也不调用模型服务或使用密钥。
写清楚过程而不是写一个脚本，是为了让结果可以被逐条复核——而不是依赖某一次生成的手感。

## 输入与产物

| 项 | 约定 |
| --- | --- |
| 输入 | 规范目录下的 `videos/<slug>/article.md`，一份观点型文章 |
| 必读参考 | [分镜脚本结构](storyboard-schema.md)、[视觉组件目录](figure-catalog.md)、[竖屏视觉规范](visual-spec.md)、[设计宪法](design-constitution.md) |
| 产物 | 该目录下的 `storyboard.json`，**唯一产物** |
| 不产出 | 视频专属画面模块（`scenes.tsx`）、图片、媒体文件、任何画面代码 |

一篇文章只对应一份分镜，位置由 [目录约定与输出路径](paths-and-outputs.md) 决定。
slug 稳定且唯一，标题变化只改 `article.md` 与分镜里的 `title`，不改目录名。

产物使用当前分镜结构版本（版本 `1`），只使用
[分镜脚本结构](storyboard-schema.md) 里已有的字段表达内容。新视频默认走
**声明式路径**：不写任何画面代码，画面由共享 React composition 加组件注册表提供，
因此分镜必须把「画面用什么表达」声明完整
（`data.figure.kind`、`labels`、`motion`、`visual.theme`、`visual.layout`）。

### 目录里已经有分镜时

这是**更新**，不是重写：

1. 先读现有分镜，把它的场景列出来，作为改动的基线；
2. 保留未修订场景的 `id`——`id` 是网页的 `data-scene-id`，改名等于换一幕；
3. 交付时说明本次改动了哪些场景：新增、删除、改写，各是哪些 `id`。

### 输入缺失或不可读时

目标目录没有 `article.md`，或文章为空、不是观点型内容时，**停止并报告**：缺哪个文件、
期望的完整路径是什么。不要凭标题猜内容，也不要产出一份占位分镜。

## 生成步骤

### 第一步：读文章，定位核心判断

先找出这篇文章**要说的那一句判断**（例如「面试不是决定命运的考试，而是一次低成本的上场」），
再找出支撑它的推理与例子。分镜是围绕这句判断组织的，不是把文章按段落平均切开。

### 第二步：按内容结构拆幕

按下面的顺序切场景。不是每篇文章都需要全部五类，但**顺序不应颠倒**——
观众的理解是层层加深的：

| 位置 | 内容角色 | 常用场景类型 | 常用组件 |
| --- | --- | --- | --- |
| 开场 | 命题、主题 | `title` | `balance` |
| 紧随其后 | 核心判断、金句 | `quote` | `gap` |
| 中段 | 对照、前后变化 | `comparison` | `versus` |
| 中段 | 过程、次数的累积 | `timeline` | `stairs` |
| 中段 | 因果链、流程步骤、反馈模型 | `diagram` | `flow`（显式声明）或 `loop` |
| 中段 | 要点清单、并列原因 | `list` | `iceberg` |
| 可选 | 数据序列：占比、趋势、构成 | `chart` | `chart` |
| 可选 | 数量、频次 | `number` | `number` |
| 收束 | 结论、行动建议 | `conclusion` | `exchange` |

要点：

- **一幕只说一件事**。一段里有两个意思就拆成两幕，不要在一幕里塞两组论点；
- **长句拆幕，不缩字号**。文案超长时拆场景，不要缩小字体或删掉核心判断；
- 场景数量由内容决定，不为了凑数补场景，也不为了省事把两幕并成一幕；
- 场景 `id` 用短横线命名，语义稳定（`opening`、`real-loss`、`fear-source`），不要用 `scene1` 这类序号。

### 第三步：决定口播与画面文案

有些场景适合口播，有些只适合看。对每一幕分别决定：

1. **口播文案**（`narration`）：观众听到的解释、例子、过渡。写完按下面的换算估时长；
2. **画面文案**（`text` / `title` / `items` / `left` / `right` / `value` 等）：画面上的字，
   只放关键结构，比口播更短、更硬；
3. **纯视觉场景**：确实不需要口播时省略 `narration`，该幕在成片里是静音的，这是允许的。

**画面文案不是口播的复制。** 口播负责解释，画面负责压住结构；两处写同一句话既浪费屏幕，
也让观众在读和听之间错过一个。

### 第四步：由口播反推时长

**先有文案，再算时长**，不要先定一个时长再往里面塞字。

- 帧数 = 秒数 × `fps`，默认 30fps，即 **1 秒 = 30 帧**；
- 中文口播按正常语速估：**每秒约 4–5 个字**。念完一句 20 字的句子约 4–5 秒 = 120–150 帧；
- 估算偏紧比偏松安全：配音较长时脚本会自动延长该幕并留 300ms 收尾，
  写得太长则画面会长时间停住；
- 每幕不少于 24 帧：更短的话入场动效会被压到看不清，通常应该并入相邻场景。

一组参考值（30fps、正常语速）：一句话的过渡幕约 90–120 帧；带完整解释判断的幕约 180–240 帧；
开场与收束可以稍长，约 150–230 帧。总时长接近或超过 180 秒时校验器会提醒——短视频应当更紧。

### 第五步：为每一幕选视觉表达

**先查组件目录，再动手。** 现有组件的适用内容与标注键见
[视觉组件目录](figure-catalog.md)；该表由组件注册表生成，是权威来源，本文不重复。

选择顺序：

1. **能在目录里找到贴切的比喻** → 声明 `data.figure.kind`、按该组件认识的键给 `labels`、
   用 `motion` 指定整幕节奏（`calm` / `normal` / `impact`）；
2. **不知道该用哪个** → 不写 `kind`，由共享 composition 按场景类型取默认组件；
3. **目录里确实没有合适的** → 走后面的「组件不足时的处理」，按注册表流程新增，不要降级凑合。

选择面的三类，按内容的**形状**挑：

- **比喻组件**（balance / gap / versus / iceberg / loop / stairs / exchange）：一段论证有一个
  可视化的「形状」——天平、落差、并排、冰山、循环、台阶、双向选择；
- **数据图表**（`chart`，场景类型 `chart`）：内容的主干是一组**数值**（占比、趋势、构成）。
  数据序列写在 `data.values`，`data.chart` 选柱状 / 折线 / 饼图；
- **关系流程图**（`flow`，场景类型 `diagram`）：内容的主干是一条**因果链或步骤序列**。
  节点写在 `data.nodes`，连线写在 `data.edges`；不写 `edges` 时按节点顺序连成链，
  要画分支或反馈回路才显式声明边。

容量与示意两条硬约束：

- **容量**：`items` / `nodes` / `values` 的条目数要落在组件声明的容量区间内
  （目录表里有列）。超出后几何会收缩、标签会挤在一起读不出来，校验器会警告；
  `--strict` 会把它当失败。宁可拆幕，不要塞容量；
- **示意标记**：画面上出现没有来源的数值时，声明 `figure.schematic: true`——
  图表组件会自动画出「示意」标；其它组件则要求标签或说明里出现「示意」二字
  （见「内容忠实与表达边界」）。

`params` **当前没有任何组件读取**，写了不改变画面，校验器会提醒，因此不要写。

### 第六步：检查排版与标注

逐幕过一遍下面这张清单。它们全部对应 `validate.py --strict` 的实际检查项，
任何一条不过都会以警告形式报出来：

| 检查项 | 要求 |
| --- | --- |
| 硬换行 | 画面文案按语义手动断行，不依赖浏览器自动折行；换行符是硬换行 |
| 单行字数 | 不超过该层级上限（正文/注释 20 字、小节标题 16 字、对比标签 8 字、列表项 14 字） |
| 场景长度 | 不少于 24 帧 |
| `emphasis` | 每个强调短语必须**原样出现**在该场景的文本字段里，否则强调色不生效 |
| 标注键 | 只使用该组件声明的键；拼错的键不报错，只会让标签空着 |
| 标注长度 | 每个值不超过 12 个汉字，过长会挤在一起读不出来 |
| 条目容量 | `items` / `nodes` / `values` 数量在该组件的容量区间内，超出后几何收缩、标签会挤在一起 |
| 未知字段 | `data` 里不出现该场景类型未定义的字段 |

## 内容忠实与表达边界

### 三条不许破的线

1. **不虚构论据、数据或来源。** 文章没有的数据不要补，需要举例时用文章里已有的例子；
2. **不扭曲原意。** 可以压缩和改写句子，但核心判断和推理方向必须保持；
3. **无来源的数值必须标注为示意。** 画面上出现任何没有来源的数字，要声明
   `figure.schematic: true`——图表组件会自动在画面画出「示意」标；其它组件
   则要求标签或说明里出现「示意」二字。两者的目的相同：让观众不会把它当成实测结果。
   校验器会核对标记真的落到了画面上。

为凑够场景数而扩充内容时，宁可合并场景，也不要引入文章里没有的东西。

### 画面表达受控

- 只用组件目录中已登记的 `kind`、受支持的 `theme`（`dark` / `light`）与 `layout`（`center` / `lower`）；
- 分镜里**不得出现** HTML、CSS、JavaScript 或第三方包引用——校验器会拒绝这类字段；
- 文案只存在于分镜里，页面与组件不保存任何默认文案。

### 必须避免的写法

- 在分镜里写页面代码或样式，或用 `params` 传几何参数；
- 先在分镜里定一个时长，再往里面塞文案；
- 把口播原文照抄进画面文案；
- 用 `Date.now()` / `Math.random()` / CSS 动画这类不可复现的表达——它们在逐帧渲染时会闪烁；
- 为一个视频新建专属画面代码（`scenes.tsx`）——声明式路径就是为此存在的。

## 组件不足时的处理

目录里确实没有能表达该段落的比喻时，**新增组件**，而不是选一个勉强接近的。

新增前必须先做两件事：

1. **检索组件目录**，确认没有可用的组件（不是「没仔细看」，而是逐条比对过）；
2. **写明差异**：新组件要表达什么，目录里最接近的是哪个，为什么它不合适。
   写不出差异说明，就说明该用的是现有组件。

确认要新增后，按 [视觉组件目录](figure-catalog.md) 的「组件契约」一节完成全部登记——
登记落在组件注册表（`web/src/registry/registry.json`，唯一真源）与渲染实现两处，
其余清单由它生成，缺一不可：

| 位置 | 要做的事 |
| --- | --- |
| `web/src/registry/registry.json` | 登记组件元数据：kind、标注键、容量、适用场景类型、实现源码位置 |
| `web/src/components/<Kind>.tsx` | 实现组件本体（帧驱动，约束见下）与配套样式（走设计令牌） |
| `web/src/registry/index.ts` | 把 kind 接到组件本体 |
| 生成命令 | `uv run python .agents/skills/article2video/scripts/sync_catalog.py` 重新生成校验器镜像、组件目录文档与 kind 枚举 |

新增组件还必须满足：

- **纯函数**：画面的每一项只由帧号、场景与时长决定，不用 `Date.now` / `performance.now` / `Math.random`，
  不用 CSS `animation` / `transition`（渲染前的静态扫描会拒绝）；
- **动效走配方层**：入场与弹性用运行时的具名预设（弹簧收秒数，不收进度），
  组件里不写自然周期、阻尼比、周期这些数字；
- **文案全部来自分镜**：组件可以决定排版，不能决定写什么，也不保存默认文案；
- **容量自适应**：条目数量变化时收缩间距与半径，而不是溢出；
- **不读实时布局**：几何由常量与实测文字宽度推导；测量只在挂载时做一次并缓存，不能每帧测。

完成后必须让机检通过：

```bash
uv run pytest tests/test_web_registry.py   # 注册表与生成物一致、声明了却没画的标注键会被拦下
pnpm -C web test                            # 渲染层消费注册表的自洽性
```

测试不通过的组件不能被分镜使用。

新增组件之后，**渲染仍然走共享声明式路径**——不要为这篇文章创建专属画面。

## 校验闭环

生成不是「写完了事」。产物要经过下面四步才算交付：

### 1. 严格校验

```bash
uv run python .agents/skills/article2video/scripts/validate.py \
  videos/<slug>/storyboard.json --declarative --strict --json
```

`--strict` 把排版类警告也当作失败，`--json` 输出 `{ok, errors[], warnings[], summary{}}`，
每条都带可定位的字段路径（例如 `scenes[2].data.figure.kind`）。

### 2. 按字段路径修正

校验失败时，按报告出的路径改**对应的那一处**，然后重跑。常见修正方向：

| 报告 | 修正 |
| --- | --- |
| 未知 `kind`、未知布局或主题、未知动效名 | 改成目录中已有的取值，或走「组件不足时的处理」 |
| 缺少必填字段 / 字段类型不对 | 补该场景 `type` 所需的字段 |
| `edges` 引用了不存在的节点 | 让 `from` / `to` 指向 `nodes` 里已有的节点 |
| 单行超长 | 在语义处硬换行，或拆成相邻场景 |
| 场景短于 24 帧 | 并入相邻场景，或按口播补足时长 |
| `emphasis` 未命中 | 改成文本中实际出现的短语，或删掉该项 |
| 强调了标注键不认识 / 标注过长 | 改用该组件声明的键，并把值缩短 |
| 未知字段、`params` | 删除——它们不产生任何画面效果 |

### 3. 无法修正时停止

同一个错误在多次修正后仍然存在时，**停下来报告**：字段路径、已经试过的修正、
以及为什么修不掉。不要交付一份没通过严格校验的分镜，也不要为了通过校验删掉核心判断。

### 4. 确认标注真的画出来了

**校验通过不等于画面正确。**「组件挂上了、画面也出来了，只是图上一个字都没有」这类缺陷
不会报错，只能靠读 DOM 发现。交付前运行组件契约探针确认：

```bash
uv run python .agents/skills/article2video/scripts/review.py \
  --storyboard videos/<slug>/storyboard.json
```

它会逐幕采样挂载点，读出的文本应当与分镜声明的标注一致；终端的「组件契约」清单
逐幕给出该幕实际使用的组件，`✓` 表示声明的标注确实画了出来。
共享 composition 的场景是运行时生成的，因此依赖源码的三项静态检查
（场景层、挂载点、文案单一真源）由渲染入口的开渲静态检查承担，
运行时结论交给这个探针。

探针发现标注缺失时，先判断是分镜写错了键，还是组件没有画这个键——
后者要回去改组件，不是改分镜。

## 交付之后

生成与校验完成后，按 [SKILL.md](../SKILL.md) 的「标准流程」继续：
预览（人工确认节奏与排版）→ 可选配音 → 渲染 → 视觉评审与成片验收。

## 命令速查

```bash
# 严格校验（生成后的第一件事）
uv run python .agents/skills/article2video/scripts/validate.py \
  videos/<slug>/storyboard.json --declarative --strict

# 预览（画面由共享 React composition 提供；不要双击 HTML，file:// 下取不到分镜）
uv run python .agents/skills/article2video/scripts/preview.py \
  --storyboard videos/<slug>/storyboard.json

# 组件契约探针 + 帧量测 + 观感/动效闸门
uv run python .agents/skills/article2video/scripts/review.py \
  --storyboard videos/<slug>/storyboard.json

# 新增组件后的一致性对照（注册表生成物与标注键机检）
uv run pytest tests/test_web_registry.py
```
