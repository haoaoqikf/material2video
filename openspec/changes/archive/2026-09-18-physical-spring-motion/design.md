# 设计：动效为什么必须可按帧求值，以及弹簧参数怎么选

## 上下文

渲染是**帧驱动**的：`seekToFrame(f)` 可以在任意顺序上被调用（渲染器逐帧推进、
review 抽帧、人工排查会直接跳到第 900 帧）。这个约束决定了动效只能是
**帧的纯函数**——`Date.now` / `performance.now` / `Math.random` /
CSS `animation` 全部被禁用，开渲前的静态扫描会拦下来。

## 决策 1：用闭式解，不用逐帧积分

弹簧求解有两条路：

| 方案 | 随机访问第 900 帧 | 复现性 | 手感 |
| --- | --- | --- | --- |
| 逐帧积分（半隐式欧拉等） | 必须从第 0 帧重放 | 依赖步长累积 | 允许任意力场 |
| **闭式解（阻尼谐振子）** | 直接算 | 同一帧必然同一结果 | 只支持线性弹簧 |

选闭式解：本项目只需要「从静止走到目标、带一点过冲」这一种运动，
而「任意帧可求值」是硬约束。积分法的浮点累积还会让同一帧在不同机器上
落到不同像素——那正是逐帧渲染最怕的东西。

## 决策 2：vendored wobble 而不是自己推

自己推闭式解不是不会（三次分支：欠阻尼 sin/cos、临界、过阻尼 sinh/cosh），
而是**已经推错过一次**：本轮实现时把初始位移写成 `x₀ = -1`（上游约定是
`x₀ = toValue - fromValue = +1`），曲线在 t 稍大于 0 时从 1.9 开始往下走——
入场从**相反方向**进来。它看起来仍然「像弹簧」，不量测就发现不了
（实测位移 −14.43px 而不是 +14.4px）。

所以：借一个成熟实现（wobble 1.5.1，MIT，2017 年起被 RN 生态大量使用），
把出处、许可证与改动写进文件头，再补一层独立核对——不是核对「我记得的数」，
而是核对解析解自己的性质（ζ=1 单调不过冲、ζ=0.62 的峰值等于
`e^(-πζ/√(1-ζ²))`、换 `response` 只改时间尺度）。

对上游的 4 处刻意改动（写在文件头）：

1. 只保留位置解（丢弃速度解），本项目只用得到位置；
2. 时间单位从毫秒改成**秒**（原实现按 ms 传参，本项目的时间全是秒）；
3. 参数改成 `response` / `dampingFraction`（自然周期与阻尼比），
   而不是上游的 「stiffness / damping / mass」——那两个系数要凑，
   这两个是可直接比较的物理量；
4. 起点固定为静止（`v₀ = 0`、`x₀ = 1`），临界分支用 `|ζ-1| < 1e-6` 判定，
   避免浮点相等把临界点漏给欠阻尼分支。

## 决策 3：`response` / `dampingFraction` 取代「阻尼 + 频率」

旧参数的问题不是数值不好，而是**两个参数都在改同一件事**：
`damping` 与 `frequency` 一起决定快慢与过冲，想「更快但一样弹」
只能试。新参数是正交的：

- `response`（自然周期，秒）→ 只决定快慢。收敛时间 ≈ `3.91/(ζω₀)`，
  ω₀ = 2π/response；
- `dampingFraction`（ζ）→ 只决定过冲，峰值 ≈ `e^(-πζ/√(1-ζ²))`。

四档预设按这个语义重排（`enter` ζ=1 一点不过冲、`firm` ζ=0.9 约 0.2%、
`lively` ζ=0.62 约 8.4%、`snap` ζ=0.8 但周期最短）。等价的旧值写在
配方表注释里，便于对照「手感是不是还差不多」。

## 决策 4：到位是一个时刻，不是一条渐近线

弹簧永远只是逼近目标。旧实现把这一层遮住了（进度到 1 直接返回 1），
换成真弹簧后暴露出来：2 秒时仍是 0.99999999999，位移永远差 0.14px。

处理方式是按**包络**判到位：`|1 - x(t)| ≤ e^(-ζω₀t)`，所以
`t_rest = ln(1/band)/(ζω₀)` 之后返回 1（band 取 0.1%，视觉上无差别）。

不用「位移进入阈值带就返回 1」：欠阻尼曲线在**第一次穿越目标时速度还很大**，
阈值法会在那一刻把它钉住，`lively` 的回弹就没了——那正是「有分量的落点」
这个预设存在的理由。

## 决策 5：缺依赖必须炸

`spring()` 读不到 `vendor/spring.js` 时直接抛错并说明「页面要在 timeline.js 之前
引入它」。不做静默回落（例如退回 `progress` 之类）：缺依赖应当表现为一次明确的
失败，而不是「动效看起来有点怪」——后者会让下一个人花一轮去查手感。

这条设计的代价立刻显形了：补上依赖时，`examples/why-effort-fails` 与
`videos/never-fear-interviews` 两个页面**渲染时直接炸**，于是漏掉的都浮出来了。
静态检查（每个加载 `timeline.js` 的页面必须先加载求解器）随后补上，
把这类问题提前到测试阶段。

## 决策 6：先有乐器，再改配方

本轮真正的产出不是弹簧，是 `tests/test_motion_trajectory.py`：
在浏览器里逐帧 `seekToFrame` 并读入场元素的 `transform`，对轨迹断言。

判据的选择依据「观众能不能看出这是滑动」：

| 判据 | 阈值 | 依据 |
| --- | --- | --- |
| 第一帧位移占比 | ≤ 25% | 旧实现 44%（更早的一版 62%），那是弹跳不是滑动 |
| 走到 90% 的帧数 | ≥ 6 帧（0.2s） | 旧实现 3 帧 |
| 到位前回退 | 不许 | 抖一下是「晃」 |
| 过冲 | ≤ 10% 全程 | surface 配方理论值 0.15% |
| 末尾位移 | 必须正好 0 | 否则元素永远停不稳 |

为什么不把它做成 K 系列闸门：K 系列是**抽帧量测**的产物，加了动效判据会让
「一次渲染」变成「必须逐帧跑一遍浏览器」——那是另一类检查（轨迹检查），
成本与触发时机都不同。它现在是 pytest 用例，理由是它与配方一起演进：
改配方的人必须同时跑它。

## 取舍与已知边界

- **只覆盖第 1 幕标题**：轨迹机检只盯一个入场元素，其余元素的入场仍无机检。
  这个覆盖面对「配方层面的倒退」够用（所有元素共用同一条曲线），
  但对「某个组件自己算错了起始帧」不够用。留作后续。
- **入场形状变了**：这是刻意的，代价是既有成片的观感会有可察觉的变化，
  需要用成片复核（已复核 `keynote-baseline` 与两篇实际文章）。
- **没有做成运行时逐帧采样**：闭式解是纯函数，测试直接调函数也能覆盖一部分；
  但纯函数测不出「组件有没有把秒算错」，所以轨迹测试是真的开浏览器。
