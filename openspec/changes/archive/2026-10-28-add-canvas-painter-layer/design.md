## Context

代码场景的截图链路已确定：`capture._capture()` 注入受控时钟，逐帧调用 `advanceToSubframe`，React 提交与绘制完成后用 CDP 截图；`lookdev` 注入了 `captureScale` 做原生 2 倍采集，并会检查所有 `<canvas>` 的后备缓冲是否足够。量测链路也已确定：`measure.DOM` 读 `[data-m2v-role]`，`measure.evaluate_probe` 读 `window.__M2V_REVIEW_STATE__`，两者在 G4 采集里同时执行。

绘制层要接入的是这两条既有链路，不是另建一套。

## Goals / Non-Goals

目标是补上 2D Canvas 这一档绘制能力，并让它从一开始就可量测、可确定、可指纹。

非目标：不替换 SVG/DOM 与三维路径；不新增第三方依赖；不改变共享字幕层；不新增门禁或审核轮次；不追溯修改既有 Canvas 作品。

## Decisions

- **绘制层带量测代理，且代理不是可选项**。核查确认：只写 `__M2V_REVIEW_STATE__` 只会新增一条"可选状态探针"检查，不会消除"观测范围：未验证"；若该帧有活动文字计划而页面没有 DOM 标记，文字状态会直接判失败，而人工证据只能替换"未验证"项、无法翻转失败。所以代理 DOM 是让画面可量测的必需项，探针降为交叉校验。
- **代理从同一份绘制数据生成**。仓库已有先例：风格包的彗尾组件视觉用 SVG，另放一个透明 `data-m2v-role` 盒做量测，几何是最接近的参考。绘制层必须比它更进一步——代理与原语共用同一次布局计算，不靠另写一套估算。
- **不新增第三方依赖**。Canvas 2D 是浏览器原生能力，打包器的批准依赖清单无需改动。
- **确定性由测试守住**。生产链路的源码闸门只扫 Remotion 入口可达图，而该入口不引用代码场景目录，因此绘制层不会自动被扫。必须仿照现有共享动效原语的测试做法，在测试里对该目录执行同一检查，并顺手覆盖宿主与 SDK。
- **文案必须由作品传入**。字体缺字检查只扫作品 `scenes/` 下的字面量，绘制层内嵌的中文会被漏掉，在浏览器里静默回退。这条写进规格，避免以后把文案挪进共享层。
- **`captureScale` 自理**。既有 SDK 的 `Canvas` 已按采集密度设置 `dpr`，`Chart` 已按密度设 `devicePixelRatio`。绘制层必须同样处理，否则 lookdev 的 2 倍采集直接失败。
- **单独命名，不与既有 `Canvas` 混淆**。SDK 已导出一个叫 `Canvas` 的 R3F 包装，新层的导出名必须区分。
- **默认 1 倍、可选 2 倍**。与既有采集约定一致，不引入第三种密度。

## Risks / Trade-offs

- **指纹失效**：新增文件进入 `implementation_inputs()`，既有作品需重新 prepare。属预期，需在交付说明中告知。
- **代理与画面不同步**：若代理与绘制各自计算几何，会出现"量测通过但画面错位"。规格要求同源，测试需覆盖几何一致。
- **两层维护成本**：多一档绘制方式意味着作者要在三种载体间选择。文档需给出选择依据：需要发光质感、高密度粒子、线条生长与逐字显影时用 2D 层；需要可选中文本、就地排版与已有风格包组件时用 DOM/SVG；需要真实三维与后期时用 three。
- **性能**：数百粒子用 Canvas 优于 DOM，但辉光出帧要多两次缩放与模糊。文档需提示按帧预算实测，不以"更快"作承诺。
- **端到端验证成本**：要求做一条原创样片并走一次核心样片独立评审，是本次最大开销；但不做就只能声称"能编译"，无法回答画面是否成立。

## Migration Plan

纯新增能力，未使用绘制层的作品画面不变。既有 Canvas 作品（`earth-night-lights`）不追溯修改，但在运行时契约里写清代理的推荐写法，供后续修订参考。完成后同步 `react-code-scenes` 主规格并归档。
