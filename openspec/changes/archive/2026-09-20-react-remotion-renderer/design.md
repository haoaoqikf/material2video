## Context

动机见 [proposal.md](proposal.md)。这里只记影响方案形状的现状与约束。

**已有的判定资产是本次迁移最大的沉没成本，也是最该保住的东西。**
`scripts/a2v/inspect.py`（33KB）、`keynote.py`（41.7KB）、`motion.py`（16.1KB）
是逐轮实测积累出来的闸门实现：K1–K10 观感闸门（含 K7 文字溢出与 K8 容器内溢出的硬判定）、
M0–M4 动效轨迹闸门、组件契约探针。它们只依赖两件事：一个可被 Playwright 驱动的页面，
和一个 `seekToFrame(frame)` 接口。

**既有渲染契约与 Remotion 的规则是同一条。** `references/render-contract.md` 禁止
CSS `animation`/`transition`、`Date.now()`、`performance.now()`、`Math.random()`；
Remotion 官方同样要求所有动画由 `useCurrentFrame()` 驱动。
所以本次迁移不需要重新论证确定性，只需要保证执行者换掉之后判据仍然量得到。

**三条已核实的外部事实决定了方案边界：**

1. Remotion 官方**没有** Framer Motion 集成
   （[Third party integrations](https://www.remotiondocs.com/docs/third-party)）。
   Magic UI 的动态文字与数字滚动、Aceternity 的 Aurora/Beam/3D Card 都建在 `motion` 上，
   属于「自带时钟」，不能直接挂进 composition。
2. CSS keyframes 类组件**可以**确定性接入：官方给出的办法是暂停自动播放、
   用负 `animation-delay` 把帧号映射成时刻。
3. Remotion 个人与 ≤3 人公司免费可商用
   （[License & Pricing](https://www.remotion.dev/docs/license/pricing)）。

**本机环境**：Node v22.23.2、pnpm 10.15.0 可用；`ffmpeg` 不在 PATH 上，
现有链路靠 `imageio-ffmpeg` 的捆绑二进制——Remotion 自带 ffmpeg，反而消掉这个隐含依赖。

**既有的「逐字节一致」不是确定性判据。** `render-contract.md` 早已写明对同一帧重复截图会
偶发出现 1 个色阶的差异，因此自动判定用的是 `PSNR ≥ 60 dB`。
规格与文档里的「逐字节一致」是**跨版本回归基线**（一个被记录下来的成片哈希），
本项目此前也刻意重录过一次（动效曲线换成物理弹簧那一轮）。本次迁移沿用同一做法：
基线在新引擎上重录一次，并说明理由。

## Goals / Non-Goals

**Goals:**

- 把画面执行与渲染换成 React + Remotion，同时让 `inspect.py` / `keynote.py` / `motion.py`
  与 `review.py` 的结论口径**一行不改**地继续成立。
- 让组件集合、标注键、容量成为一份注册表，派生文件由它生成。
- 补上已登记的数据图表缺口，并让关系流程类画面可用。
- 给出「第三方组件能不能用、要怎么用」的可执行判据，而不是一条口头原则。

**Non-Goals:**

- 不改 `storyboard.json` 的结构与字段语义。旧分镜不需要改写。
- 不把配音与字幕准备搬到 Node。现有 `prepare.py` 的缓存、分幕延长与字幕分句都工作得很好。
- 不引入 3D（Three.js）、Lottie、Skia。它们都有官方集成，但当前没有内容需求；
  留给以后的独立提案。
- 不做交互式剪辑界面（Remotion Studio 的编辑态、React Flow 的拖拽编辑）。
- 不追求与旧成片逐字节一致——引擎不同，这个目标不可达，且与项目既有判据不一致。
- 不在本次提案里实现 20–30 个组件。本次定义注册表机制与组件类别，
  具体清单按内容需求分批落地。

## Decisions

### 决定 1：用 Remotion Player 复现 `__A2V__` 契约（version 2）

**选择**：把 composition 挂进一个页面，用 `@remotion/player` 的 `seekTo(frame)` 实现
`seekToFrame`，暴露 `window.__A2V__` version 2。体检与量测继续用 Playwright 驱动这个页面。

**为什么**：这让约 90KB 已实测的判定逻辑原样继续工作。闸门量的是 DOM 结构、元素文本、
逐帧不透明度与位移——这些与「画面由谁渲染」无关，只与「怎么寻址一帧」有关。
重写闸门的代价不是工作量，而是**判定口径会漂**：K7 的 8px 容差、K8 的 2px 容差、
M 系列的 25% / 6 帧 / 12 帧门槛都是从真实缺陷里反推出来的，重写一遍必然重新引入盲区。

**否决的替代方案**：

- *在 Node 侧用 Puppeteer 直连 Remotion bundle 重写全部闸门*：判定口径漂移风险最高，
  且要同时维护两套语言的门槛常量。
- *不提供契约页，体检改用抽帧图片做纯图像分析*：K4 对齐基线与 K6 卡片纪律需要 DOM
  （元素框、文本样张、字号），纯图像做不到；组件契约探针更是必须读 DOM 文本。

### 决定 2：`__A2V__` 升到 version 2 而不是保持 version 1

**选择**：版本号升到 2。

**为什么**：`ready()` 的语义扩大了（要保证 Player 已挂载、首批字体已加载），
`seekToFrame` 的实现在外部（Player），并且旧实现者（自建 `timeline.js`）在迁移后不再存在。
版本号是唯一能让「渲染脚本因为加载了旧页面而报错」变成**明确错误**而不是
「等超时后报一句看不懂的话」的手段。

**否决的替代方案**：*保持 version 1* —— 会让版本号失去意义，而这次恰好是第一个
「实现者换人」的场景，正是版本号该发挥作用的时候。

### 决定 3：Python 与 Node 分工按「谁需要浏览器」切

**选择**：Python 保留分镜校验、路径归属推导、配音与字幕准备、体检编排、溯源、交付文件权限修复；
Node 只负责逐帧渲染与编码，以及画面本身的执行。

**为什么**：这条切法让**离线与可测的部分留在 Python**（校验、路径、字幕、溯源都是纯文件逻辑，
36 个测试文件里绝大多数在测它们），把必须跑浏览器的部分交给 Node。
更重要的是：`prepare.py` 的 TTS 缓存、按配音延长场景、字词时间戳分句都已实测可用，
搬到 Node 只会重造一遍并丢掉缓存兼容性。

**否决的替代方案**：*全量迁到 Node* —— 会让 `assets.py` 的指纹算法、`paths.py` 的双根推导、
`security.py` 的 ACL 修复全部重写，而这些恰好是最容易出静默错误、最需要保持逐字节行为的部分。

### 决定 4：第三方组件按动画机制三分类，C 类必须改写

**选择**：分三类。纯静态类直接接入；CSS 动画类经帧同步包装接入；自带时钟类**必须改写**为帧驱动。

**为什么**：这是「想直接用现成组件」这条诉求唯一诚实的落法。生态里最好用的那批组件
（动态文字、数字滚动、粒子、光效）恰好都在第三类，因为它们的卖点就是「自动播放」。
只允许前两类、禁止第三类，等于放弃清单里最想要的部分；允许第三类直接接入，
等于把确定性交给运气——「偶尔不闪」不能证明确定性。

**落地方式**：第三方组件的源码以源码形式进入仓库（shadcn 模式），许可证与来源随资产记录。
这样改写是合法的、可追溯的，也不会因为上游发版而静默漂移。

**本次落地范围**：只选 1 个 CSS keyframes 类组件作为代表，证明「分类表 → 帧同步包装 →
源码机检 → 同帧确定性」整条机制成立。组件数量不是本次目标；在没有真实文章需求前批量引入
5 个组件，只会扩大许可、视觉回归与维护面。自带时钟类保留“使用前必须改写”的规则，
本次记录时间盒判断但不把第二个实验组件带入正式注册表。

**否决的替代方案**：

- *只做前两类*：D 类清单里最想要的组件全拿不到，等于没解决原始诉求。
- *直接依赖动画库并「尽量少用」*：与既有静态扫描闸门正面冲突，且会把
  「预览正常、导出闪烁」重新引进来——这正是本项目当初设立扫描闸门要防的问题。

### 决定 5：关系流程用纯函数布局 + 自绘 SVG，不用 React Flow

**选择**：`dagre`（分层布局，纯函数）算一次布局，用受控的 SVG 渲染节点与连线。

**为什么**：React Flow 的设计目标是交互式编辑器，它的节点尺寸测量与 `fitView()`
依赖异步布局与 `requestAnimationFrame`（[xyflow#4801](https://github.com/xyflow/xyflow/issues/4801)
即 `fitView()` 初始化后偶发失效）。在逐帧随机访问的渲染里，「偶发失效」就是闪烁。
而分级布局本身只需要一个纯函数——节点位置由节点文本与图层决定，算一次即可缓存。

**代价**：失去 React Flow 的交互能力（拖拽、缩放、自动连线路由）。这在渲染路径上不需要；
若以后要做编辑界面，可以把 React Flow 只用在编辑态。

### 决定 6：图表用 ECharts，但关掉它自己的动画

**选择**：`echarts/core` 按需引入，`animation: false`，每帧只喂由帧号算出的数据切片与逐点进度，
渲染到 canvas。

**为什么**：ECharts 的配置是纯数据，只要关掉它内部的动画循环，逐帧 `setOption` 就是确定性的；
它的能力覆盖（柱、折线、饼、坐标轴、标签避让）远超过自绘。自绘图表在「标签避让」
与「中文轴标签」上会反复踩坑。

**代价**：canvas 渲染让 DOM 探针读不到图表内的文字，K7/K8 这类基于元素框的判定
对图表内部不适用。**这一点必须如实记录**：图表的可读性判定需要另一套手段
（在组件里把关键数值同时以 DOM 文本呈现），否则图表会成为闸门的盲区——
本项目对盲区的立场是「如实报跳过并写明原因」，不是「静默放过」。

### 决定 7：动效原语照搬闭式弹簧与配方数值，不用 Remotion 自带的 `spring()`

**选择**：把 `assets/vendor/spring.js` 的阻尼谐振子闭式解移植为 TS 模块，
`response` / `dampingFraction` 参数与配方表数值照搬。

**为什么**：Remotion 的 `spring()` 参数是 `damping`（0–200）、`mass`、`stiffness`，
与这里的物理量不是同一组；换过去就意味着 M 系列的实测轨迹与门槛失去可比性，
而 `tests/test_motion_trajectory.py` 的每一个门槛都是从真实缺陷反推出来的。

**否决的替代方案**：*直接用 Remotion `spring()` 并重录门槛* —— 等于把半年量出来的
轨迹判据全部作废，代价远大于移植一个闭式解。

### 决定 8：保留同名的 CSS 变量、基元类与 `data-a2v-*` 属性

**选择**：令牌名（`--a2v-*` / `--fig-*`）、基元类（`a2v-surface` / `a2v-label` /
`a2v-connector` / `a2v-frame`）、状态属性（`data-a2v-state`）与测量属性
（`data-a2v-inside` / `data-a2v-fit`）全部保持同名。令牌真源仍是一份 CSS 文件
（Tailwind v4 的 `@theme` 会把它们编译成同名 CSS 变量），组件用 `var(--令牌, 原值)` 引用。

**为什么**：这些名字是**机检的锚点**。K8 靠 `data-a2v-inside` 找容器，
K 系列靠基元类找卡片与焦点，令牌闭包断言靠 `--fig-*` 的名字。
改名不会报错，只会让闸门**静默跳过**——本项目已经吃过一次这个亏
（K6 因为只取挂载点直接子元素而长期报「没有可识别的卡片表面」）。
保持同名还有一个副作用是好的：`openspec/specs/keynote-design-system` 里
关于令牌与基元的绝大多数要求可以逐字保留，不需要重写。

**否决的替代方案**：*改成 Tailwind 工具类与 TS 常量* —— 更「现代」，
但会让几百条基于名字的断言与闸门同时失效，且没有可验证的收益。

### 决定 9：确定性以 PSNR ≥ 60 dB 判定，回归基线在新引擎上重录一次

**选择**：沿用 `render-contract.md` 既有的 `PSNR ≥ 60 dB` 阈值；旧引擎上记录的
成片哈希在新引擎上重录一次，并在文档里写明这次重录的理由。

**为什么**：逐字节相等在换无头浏览器发行版后不可达（光栅化噪声），
而项目自己的契约文档早就改用 PSNR 了。K 系列、M 系列与字体缺字机检的**数值门槛
一个都不放宽**——放宽它们才是真的降低标准。

**否决的替代方案**：*坚持逐字节* —— 会因为不可达而被迫频繁「重新记录哈希」，
使这条证明退化成噪音；本项目已经明确写过「闸门变成噪音等于没有闸门」。

### 决定 10：作品专属画面是 React 模块，由生成的动态入口引入

**选择**：作品目录下放画面模块，工具按工作区根生成前端工程的动态入口引用它；
入口目录由工具生成、不入库。

**为什么**：这是「AI 做导演不做设计师」与「确实需要目录外构图」之间必须留出的逃生口。
生成入口是为了让**内容根位于仓库之外**时仍能被构建工具解析到——
前端构建器不会去猜仓库外的路径。

**边界**：专属画面模块 SHALL 由受控组件组合而成；它 SHALL NOT 引入未改造的第三方动画。
也就是说，逃生口允许新的**构图**，不允许新的**动画机制**。

## Risks / Trade-offs

- **C 类第三方组件的改写量可能超出预期** → 本次不把 C 类实验组件带入正式注册表；
  先用一个 B 类代表组件证明适配机制，并记录 C 类必须改写的成本判断。真实内容提出明确需求后，
  再为对应组件单独时间盒，而不是预先批量囤积组件。
- **闸门因为改名或结构变化而静默失效** → 这是本迁移最大的隐性风险。
  缓解：保留同名锚点（决定 8）；阶段 2 强制先跑一次「旧路径与新路径的 K/M 结论对照」，
  逐项核对通过/提醒/跳过的数量与内容，而不是只看错误数是否为 0。
- **迁移期双栈并存产生假信心** → 阶段 2 起以新路径为唯一验收口径，
  旧路径只作为对照基线存在；每个阶段的验收都要求旧基线不劣化，而不是要求两边都通过。
- **图表内部成为闸门盲区** → 如实记录：canvas 内的文字不受 K7/K8 约束。
  缓解手段是要求图表组件把关键数值同时输出为 DOM 文本；未覆盖的部分在体检报告里
  报「跳过并写明原因」，而不是静默通过。
- **Node 成为硬前置依赖** → 缺少前端依赖时必须明确报错并说明安装方式，
  SHALL NOT 产出空成片。渲染期仍需离线可用（依赖已安装的前提下）。
- **Remotion 许可证的越界条件容易被忽略** → 写进 `web/README.md`：
  个人与 ≤3 人公司免费；4 人以上协作或对外提供渲染服务需升级。
- **Playwright 的用途收窄但没消失** → 它从「渲染器」变成「体检探针的驱动」。
  这一点要在 README 里写清楚，否则以后会有人以为可以删掉它。

## Migration Plan

阶段划分与逐项任务见 [tasks.md](tasks.md)。这里只记顺序上的约束与回滚。

1. **阶段 0**：本提案。必须先拿到规格与任务的认可，再动代码。
2. **阶段 1（骨架 + 契约）**：先让契约页与 `__A2V__` version 2 成立，再谈组件。
   这一阶段的验收是「体检能对着一个空画面正常工作」——先把测量通道打通，再往里填画面。
3. **阶段 2（组件等价迁移）**：一次一个组件，每个组件迁完立刻跑该组件相关的
   K 系列条目与 M 系列轨迹。**不允许批量迁完再一起验**：一旦批量迁移后再发现
   结论漂移，无法定位是哪个组件引起的。
4. **阶段 3（第三方接入层）**：先做 CSS 动画包装层（B 类，收益确定），
   用 1 个代表组件验证确定性；C 类只记录接入判据与成本结论，不在本次进入正式注册表。
5. **阶段 4（图表与关系图）**：在注册表机制建立之后做，因为这两类需要新增 kind。
6. **阶段 5（编排面收口）**：注册表生成物接管 catalog 与文档。
7. **阶段 6（切换与删除）**：**只有在三支示例与一篇实际作品全部在新路径上通过之后**，
   才把默认切到新引擎并删除旧资产。

**回滚策略**：每个阶段一个 commit，旧管线在阶段 6 才删除。
因此阶段 1–5 期间的回滚一律是「回退该阶段的 commit」；
阶段 6 之后若发现新引擎有阻塞问题，回滚点仍是阶段 5 的 commit，
此时旧管线完整可用。这也是把删除放在最后一步的全部理由。
