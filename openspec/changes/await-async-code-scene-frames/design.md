## Context

既有宿主flushSync更新elapsedSeconds，再刷新受控RAF/计时器并等待paint；资源ready只处理字体。WebGPU异步渲染可能在该屏障后才完成，当前上下文没有让宿主等待工作的接口。

## Goals / Non-Goals

目标是在不使用挂钟驱动画面、不修改材料格式的前提下，提供明确的异步绘制完成边界。非目标：替任意库认证确定性、隐式发现所有异步工作、改变超时或允许远程资源。

## Decisions

1. SceneContext新增waitForFrame(task: PromiseLike<unknown>): void。参数须为可等待对象；登记后立即吸收拒绝并保留结果，避免在宿主开始等待前出现未处理拒绝；完成收集时重新传播错误。
2. 每个宿主持有任务队列。帧提交串行：begin拒绝重叠；受控时钟flush后等待队列（包括链式新增任务），随后仅执行原生paint屏障，再检查是否有新登记工作。任务失败不得更新成功帧号。
3. 初始ready只创建一份就绪Promise，等待字体、队列和paint。start引发的effect任务保留给首个帧提交。登记须由受控状态更新驱动；接口不为挂钟、随机或未登记工作兜底。
4. capture-clock只向宿主暴露既有内部paint函数；不再推进虚拟时间或触发新的用户RAF，避免异步完成后重新启动另一轮绘制。
5. 不修改现有30秒就绪/逐帧deadline。未完成任务仍超时失败；纯时间需继续正反序及跨加载验证。
6. 可执行最小示例使用OffscreenCanvas.convertToBlob和createImageBitmap完成原生异步绘制；同一示例进入真实浏览器测试，不新增第八部视频示例。另验证现有同步场景节点。

## Risks / Trade-offs

漏登记工作仍是作品实现错误；无限链式登记由既有超时收敛。新接口不使状态式渲染自动纯时间。GPU模型初始化和资源恢复仍须在ready前完成。运行时源码变动使旧缓存/样品来源失效，最终样品要重采集。

## Validation

队列独立测试覆盖多任务、链式任务、拒绝、非法输入、重叠提交与失败恢复；真实采集验证顺序、pure-time正反序、子帧/首次绘制等待及异步失败不发布。只运行直接相关节点和一个现有同步场景，不跑全仓。


## 实施验证与独立审查

- 队列5项Vitest通过；最终运行时web typecheck通过。真实浏览器验证异步Bitmap初始/启动等待、绝对seek与子帧；原生1920×1080纯时间4帧编码、像素及正反序探针通过，登记任务拒绝不发布采集。既有DOM/Three/Motion/GSAP/CSS61帧同步与既有pure seek节点通过。七示例中只补充fold材料与全部场景构建节点，未运行全仓。
- 主代理复核发现启动旧帧与首个seek并行覆盖的风险，独立审查确认；已在改变时间前先收敛启动任务，新增受控门闩浏览器回归验证旧帧8等待期间不变、并发seek拒绝、释放后帧3像素正确。最终关联4节点均通过。
- 独立代理另在真实Chromium验证重叠拒绝、未完成任务等待/释放、deadline超时后仍互斥及受控时间不推进；复核修复后无阻断发现，质量96/100。
- 性能：同步零额外paint，仅常数级队列检查/微任务；异步时间与内存随登记任务数线性增长。未做吞吐基准，未据此认证复杂GPU动态。
- 局限：未登记或提前resolve的工作、外部GPU状态与确定性由作品负责，后续正文仍须实际验证。初次测试夹具误用不支持的320×240，已改为正式1920×1080后通过；没有放宽画幅或超时门禁。
