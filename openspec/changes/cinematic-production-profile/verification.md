### 与任务措辞的一处偏离（2.3）

任务写「镜头时间窗落在旁白段内」。按 60 秒样例的实际时长分布（9 段旁白各约 5–7 秒）与「hero 必须 8–12 秒连续」的硬要求，把 hero 限制在**单段旁白内**在数学上不成立。因此实现的判定是：

- 每个镜头必须落在本幕时长内；
- **声明** `segment` 的镜头必须**完整覆盖**该旁白段的窗口（这是作者对「这个镜头讲的就是这段旁白」的承诺）；
- 没有声明 `segment` 的镜头只查幕时长——冷开场、收尾与跨段 hero 都属于这一类。

`claims` 与镜头的可见性对应关系由 QA 的 claims 检查负责（每条 claims 必须落在至少一个镜头的时间窗内）。该口径已同步写入 `storyboard-schema.md` 与 `cinematic-video.md`。

### 运动模糊与 SSAA（3.5）

- 录制协议扩展为**子帧**：宿主新增 `advanceToSubframe(frame, subframe, subframes)`，上下文时间为
  `(frame + subframe / subframes) / fps`，React 状态、三维绘制、动画库、CSS 动画与本地视频都停在同一
  时刻；`advanceToFrame(n)` 等价于「第 n 帧的第 0 个子帧」，因此两种推进可以混用。协议只接受连续
  推进（同帧子帧递增，或进入下一帧的第 0 个子帧），乱序立即失败。
- 子帧数只对 **hero 镜头内**的帧生效（`look.motion.subframes`，1–4），其余镜头保持单帧；Python 侧把
  子帧等权平均成一张输出帧。平均用 `mix`（等权归一化）而不是 `blend=all_mode=average`：后者对同一组
  0/128/255 的子帧给出 159 而不是 128，不能当作平均。
- SSAA：`look.motion.supersample: 2` 时用 CDP `clip.scale` 按 2 倍设备像素截图（裸的
  `Page.captureScreenshot` 只按 CSS 像素出图，`device_scale_factor` 不体现在结果里），编码时用
  lanczos 降采样回目标画幅。
- `motion` 只在作品显式声明时进入录制配置，standard 作品的缓存键与画面保持逐字节不变。

### 真实浏览器验证（新增 `tests/test_cinematic_scene_kit.py` 9 项、`tests/test_cinematic_motion.py` 11 项）

- **镜头确实在动**：同一镜头首末帧 PSNR < 40。
- **后期生效**：开与关后期的同一帧 PSNR < 45。

- **套件自身过确定性闸门**：对 `cinematic.tsx` 跑 `source_policy.scan` 无违规。
- **穿球与背景裁切检查**：纯函数结果在页面内直接断言（命中、未命中、余量不足、星空壳外与超出远裁剪面）。
- 另有 Python 侧用例覆盖缺依赖提前失败、`lut` 非法值、`useMediaAsset` 新字段。
- **运动模糊与 SSAA 走真实采集路径**：小画幅下真跑 `_capture`（Playwright + CDP + 子帧平均），

  「只取一个子帧」的同一帧画面不同（否则模糊是假的）；子帧协议的时间与乱序拒绝也在真实页面里断言。

### 地球 hero 的表面细节（4.5 的一部分）

- 用标准材质的 `onBeforeCompile` 注入三项，不另写一套光照：**夜面城市灯光**（陆地掩码 × 夜面掩码 × 物体空间哈希点阵的自发光）、**海面高光**（按陆地/海洋改粗糙度，海洋 0.14 / 陆地 0.86）、**云影**（把云层 alpha 图乘到反照率上）。

### 声音设计（4.8）

- 音乐床与三个音效由 `assets/sound/generate.py` **原创合成**（正弦、相位调制与确定性伪随机噪声，无第三方采样），按 CC0 1.0 分发并附 `LICENSE.md`。素材随仓库版本控制，与缓冲示例的音床做法一致。
- 音乐床 16 秒 / 60 BPM：低频 drone（55/82.5/110 Hz）+ 相位调制的 pad + 每拍一次的柔和脉冲。**无缝循环按契约判据构造**：所有频率都取循环长度的整数分之一，漂移只用相位调制，因此末采样到首采样的步进不超过素材内部的最大相邻步进。
- 音效：`whoosh`（飞近，带通噪声包络 + 下行低频）、`shimmer`（环的泛音簇衰减）、`ice`（冰裂爆裂 + 三条固定共振）；章节切换仍用内置 `transition`。分镜的 `soundtrack` 声明音床（−30 dB、循环、2.5 秒淡入 / 4 秒淡出）与三个本地音效的定位与增益。
- 验证：循环接缝判据、峰值不削顶、ffmpeg 可解码、分镜声明与真实文件一致、生成器重跑得到逐字节相同的素材。

### 单帧成本实测与采集提速（4.9 的前置量测）

设计要求在 look-dev 阶段先量一次单帧成本，避免整片渲完才发现预算失控。实测（同一场景 12 帧，1920×1080）：

| 设置 | 软件光栅化 | 打开 GPU 后 |
|---|---|---|
| 关闭后期 / 1× / 1 子帧 | 0.94 帧/秒 | 1.66 帧/秒 |
| Bloom+grain+vignette / 1× | 0.74 | 1.50 |
| 再加 DOF 0.5 / 1× | 0.39 | 1.48 |
| DOF 0.5 / 2× SSAA | 0.39 | 1.47 |
| DOF 0.5 / 2× / 2 子帧 | 0.39 | 1.49 |

两个结论：**DOF 在软件光栅化下是主要瓶颈**（0.74 → 0.39，几乎翻倍），而 **2× SSAA 与子帧几乎免费**（瓶颈在渲染与后期，不在截图像素数）；整片 3824 帧按当前设置约 43 分钟（不含 hero 的多子帧）。

根因是默认无头 Chromium 走 **SwiftShader 软件光栅化**：本机有 Intel Arc GPU，显式打开 `--use-gl=angle --use-angle=d3d11 --ignore-gpu-blocklist` 后实测提速 1.8～3.8 倍，DOF 从 0.39 提到 1.48 帧/秒。没有可用 GPU 的环境会自动回退软件光栅化，因此这是提速而不是新的硬依赖；同帧可复现性不受影响（两次独立录制的 PSNR ≥ 60dB 仍然通过）。

### 已知脆弱点：整幕录制不可续

代码场景片段是**整幕录完才落盘**的（逐帧 PNG 在临时目录里，全部采集并编码成功后才交付到 `outputs/code-cache/`）。60 秒成片只有一幕，因此这一份准备必须**一次不中断**跑完：中途被杀会丢掉全部进度，只留下临时 PNG 目录。实测已被中断过一次（只留下 185 张 PNG）。

当前按 GPU 光栅化 + hero 2 子帧 / 2× SSAA 的实测速率是 1.2～3.0 帧/秒，整片约需 50～60 分钟，落在这个脆弱点的影响范围内。**按段或按帧检查点续录**是这条链路真实缺的能力，计划在阶段 6 之前补上，而不是依赖会话不重启。


**微基准的适用条件（事后修正）**：上面 12 帧的量测里 hero 只占 25%，且以渲染为瓶颈，因此得出「2x SSAA 与子帧几乎免费」。在真实成片里 hero 占 40%，4K 截图的 PNG 编码与落盘成为主导：hero 段实测只有约 0.26 输出帧/秒（每帧 4 张 4K 截图），整段平均约 1.0 张/秒。**成本结论必须标注占比与瓶颈位置**，否则按微基准做预算会低估 hero 段约 4 倍。

**4K 采集的决定与实测**：成片最初按 `supersample: 2` 录制，hero 段实测只有 **0.2 输出帧/秒**（每帧 2 子帧 × 4K 截图约 8～10 秒），整片将达约 4.5 小时，不可接受。改为 `supersample: 1` 后同一段落实测 **3.4 张/秒**（约 17 倍），整片约 25 分钟。

因此示例成片采用 **1× 采集 + 2 子帧运动模糊**：hero 的运动模糊保留；**4K 超采样改由 `m2v lookdev` 的 2× 静帧渲染承担**（那一条路径只渲染 3～5 帧，成本可忽略）。`supersample` 能力本身仍然实现并有单元测试覆盖，只是示例成片不启用——这是成本与画质的取舍，不是能力缺失。

**子帧平均的隐藏成本**：1x 采集 + 2 子帧时 hero 段实测只有约 0.33 输出帧/秒，明显低于「2 张截图」应有的速度。原因不是渲染或截图，而是**逐帧起一次 ffmpeg 进程**做子帧平均（本机没有 numpy/Pillow，无法在进程内平均）：每帧多出约 1 秒的进程启动开销。

示例成片因此暂时采用 `subframes: 1`（实测 2.6 张/秒，整片约 25 分钟）。**运动模糊能力本身已实现并有真机用例覆盖**（「取两个子帧与只取一个子帧的画面必须不同」），缺的是把它用到成片上的成本。改进方向已明确：把逐帧平均改成**按幕批量**——把一幕的子帧按顺序写成序列，用一次 ffmpeg 的 `tmix=frames=N` + 按组取帧完成平均（每幕一次进程调用而不是每帧一次）。
