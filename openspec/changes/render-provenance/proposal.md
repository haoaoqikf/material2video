# 提案：成片的溯源与陈旧判定

## Why

第 8 轮实测踩到一个死角：**所有机检都在源码侧，产物侧没有任何溯源**。

- 两支实际作品的成片比动效重写早了几个小时，仍然带着被修掉的 3 帧弹跳；
- 而它们看上去仍然是「上次验收通过」的样子——`outputs/` 不入库，
  没有任何东西会提醒；
- 只能靠人比对文件时间戳发现，然后手工重渲。

同一个仓库里已经有现成的先例：**媒体清单已经有这套纪律**。`media.json` 记
`sourceFingerprint`，`render.py` 在加载时比对它，不一致就报
「分镜已修改，请重新 prepare」（第 8 轮正是这条拦下了 `why-effort-fails`）。
成片这一侧缺同样的一层。

## What Changes

- 渲染成功后落一份溯源伴随文件（默认与成片同目录、同主名），记录：
  页面与分镜路径、**涉及资产的指纹**（网页引用的本地样式表与脚本，含 skill 的共享资产）、
  帧数、时长、分辨率与帧率、采集格式、渲染时刻。
- 验收命令能据此回答「这个成片是不是旧资产渲的」：指纹不一致时报出来，
  指出是哪些文件变了；缺失溯源时如实说「无法判断」，**不得默认放行**。
- 指纹口径与媒体清单保持一致（同一套哈希与字段命名），不另造一套。

## Impact

- 不改画面：成片逐字节不变（只是多写一个伴随文件）。
- 不改分镜结构与渲染契约；`outputs/` 仍不入库。
- 新增机检：改了资产之后，已有成片必须被判定为落后（反例要真的能报出来）。
